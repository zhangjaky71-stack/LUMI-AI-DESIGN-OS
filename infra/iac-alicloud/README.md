# LUMI Alibaba Cloud staging infrastructure

This directory is the Alibaba Cloud migration path for the existing AWS reference deployment. It is intentionally additive until staging parity is proven; the AWS implementation remains available as a rollback/reference path.

## Selected region and zones

- Region: `cn-hangzhou`
- Zones: `cn-hangzhou-h`, `cn-hangzhou-i`, `cn-hangzhou-j`
- Account: `1153410507483251`
- Local OAuth profile: `lumi-deploy`

Hangzhou was selected after API preflight showed VSwitch, PostgreSQL 15 and Redis availability and because SAE was not available in the former Tokyo candidate region. The three zones above were selected from the intersection of the required service availability results, not merely the first three ECS zones.

## Directory model

```text
bootstrap/
  OSS remote-state bucket
  TableStore lock instance/table
  GitHub Actions OIDC provider
  branch-bound RAM role and least-privilege ACR push policy

core/
  VPC and three network tiers
  per-zone NAT egress
  three private OSS application buckets
  RDS PostgreSQL 15
  Redis-compatible cache/session store
  six ACR repositories
  six SLS logstores
  ACK Managed Pro cluster in Auto Mode with RRSA and private control plane
  optional RabbitMQ instance and canonical queue topology

k8s/
  seven persistent workloads and five private ClusterIP services
  ALB HTTPS ingress contract
  namespace, least-privilege Sandbox Job RBAC and network policies
  one-shot Alembic migration Job
  non-applied Secret shape example
```

The ACK layer uses immutable `repository@sha256:...` images. The Sandbox Runtime creates one short-lived, digest-pinned Kubernetes Job per execution and retains the AWS ECS implementation as a rollback/reference path. Alibaba OSS is accessed through the internal S3-compatible endpoint using Signature V2 and virtual-host addressing; AWS continues to default to Signature V4.

## Service activation gate

Open the Alibaba Cloud console and activate these services for `cn-hangzhou`:

1. Object Storage Service (OSS)
2. TableStore
3. Container Registry (ACR)
4. ApsaraDB RDS for PostgreSQL
5. Tair/Redis-compatible
6. Message Queue for RabbitMQ
7. Simple Log Service (SLS)
8. Container Service for Kubernetes (ACK) and Elastic Container Instance (ECI)

Service activation and billing agreement acceptance are account-owner actions. Terraform must not be applied until those terms and the estimated recurring cost have been reviewed.

## Safe execution order

```powershell
terraform -chdir=infra/iac-alicloud/bootstrap init
terraform -chdir=infra/iac-alicloud/bootstrap plan
terraform -chdir=infra/iac-alicloud/bootstrap apply

terraform -chdir=infra/iac-alicloud/core init `
  -backend-config=backend.hcl
terraform -chdir=infra/iac-alicloud/core plan
```

Create an ignored copy before the core commands:

- `core/backend.hcl` from `core/backend.hcl.example`

Never commit `backend.hcl`. The OSS backend must receive the OAuth profile's temporary access key, secret and Security Token through process-only environment variables because Terraform Core does not understand Alibaba Cloud OAuth profiles. On this host, set `GODEBUG=http2client=0` only for the Terraform subprocess so the TableStore backend is not reset by the local tunnel, then clear it. RDS, migration-account and Redis passwords are generated by Terraform and exist only as sensitive values in encrypted remote state; do not print them or store them in CI logs.

The image workflow uses GitHub Actions OIDC instead of GitHub repository secrets. Its trust policy accepts only the exact subject `repo:zhangjaky71-stack/LUMI-AI-DESIGN-OS:ref:refs/heads/codex/alicloud-deployment`, exchanges that identity for a short-lived RAM role session, then requests a temporary ACR Personal Edition token. The role can only request an ACR authorization token and pull or push repositories under `acs:cr:cn-hangzhou:1153410507483251:repository/lumistaging3251/*`. Alibaba Cloud login names, the fixed Registry password and long-lived AccessKeys must never be saved in GitHub.

The OIDC provider pins the SHA-1 fingerprint of the self-signed `ISRG Root X1` CA currently serving GitHub's token endpoint. Revalidate that public CA fingerprint before its certificate expires or when GitHub announces an OIDC certificate-chain change.

After a reviewed Core apply, the release sequence is:

1. Run `.github/workflows/build-alicloud-runtime-images.yml` on the exact release commit and download its six-image digest manifest.
2. Replace every `REPLACE_WITH_*` deployment value from verified Terraform output, the frozen image manifest, and the approved TLS domain/certificate.
3. Create `lumi-runtime-secrets`, `lumi-oss-runtime`, and `lumi-oss-sandbox` through the protected operations path. `secrets.example.yaml` is a schema example and is deliberately excluded from Kustomize.
4. Apply `k8s/migration`, wait for `lumi-database-migration` to exit successfully, and verify Alembic head `0023_video_generation_runtime`.
5. Apply `k8s/base`, wait for all seven rollouts, then collect health, queue, database, OSS and end-to-end smoke evidence.

## Current state and hard blockers

- The OSS state bucket is live with private ACL, versioning, AES256 encryption and public-access blocking.
- TableStore instance `lumi-tf-3251` and table `terraform_lock` are live. The table is imported into Bootstrap state, and Bootstrap plans with zero changes.
- GitHub OIDC provider `lumi-github-actions`, RAM role `lumi-github-acr-push`, custom policy `LumiGitHubAcrPush` and their attachment are live. The role trust is restricted to this repository's `codex/alicloud-deployment` branch, and the policy is restricted to the staging ACR namespace.
- The ACR Personal Edition instance is live in `cn-hangzhou`, and the account owner has set its fixed Registry password. Namespace/repository creation remains part of the unapplied Core plan.
- Core is initialized against OSS with TableStore locking. The current reviewed-shape plan is `67 add / 0 change / 0 destroy`, including ACK and the migration account; it has not been applied.
- The remaining paid services have not been verified by a real apply.
- The Alibaba Cloud account currently reports `¥0.00` available balance, so paid Core resources cannot be applied until the account owner funds the account and explicitly approves the recurring-cost plan.
- RabbitMQ is deliberately disabled by default until its service and price are approved.
- ACR Personal Edition resources are deprecated in Alibaba Cloud Provider `1.291.0`; they are only a staging bridge.
- GitHub CLI authentication is invalid. The hosted ACR build workflow exists and branch `codex/alicloud-deployment` has been pushed. The workflow source now uses the live GitHub OIDC role and temporary ACR tokens, so no Alibaba Cloud username, fixed Registry password or long-lived AccessKey is required in GitHub.
- Local Docker daemon is unavailable, so the six runtime images must be built by the hosted workflow.
- ACK manifests and migration Job exist but still contain explicit `REPLACE_WITH_*` gates. No migration execution, workload rollout, health check or staging smoke evidence exists yet.

These sources and the bootstrap resources are not evidence that the LUMI application is live.
